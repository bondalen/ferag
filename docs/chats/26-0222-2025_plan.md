## Задача плана (один чат)

Реализовать **сессии диалогов**: один пользователь может вести с одним RAG несколько диалогов (разные темы). Добавить таблицу `chat_sessions`, привязку сообщений к сессии (`session_id` в `chat_messages`), CRUD по сессиям на backend и выбор/создание сессии во frontend. Роли (owner, editor, viewer) уже обеспечиваются `_can_access_rag` и проверкой «только свои сессии»; при реализации явно соблюдать видимость: участник не видит RAG и чаты, куда его не приглашали.

**Последующие задачи (вне объёма данного чата):** сжатие длинных диалогов (задача 9.13): резюме старой части + последние K пар + текущий вопрос в запросе к LLM; при необходимости — хранение резюме, пороговая или периодическая суммаризация. См. [PROJECT-004-chat-dialogue](../project/PROJECT-004-chat-dialogue.md), разд. 5–6.

---

## Исходное состояние

- Таблица `chat_messages`: `id`, `rag_id`, `user_id`, `role`, `content`, `context_used`, `created_at`. Поля `session_id` нет; все сообщения пользователя по RAG в одном логическом потоке.
- `POST /rags/{rag_id}/chat` — пишет две записи в `chat_messages` (user, assistant). Параметр сессии не принимает.
- `GET /rags/{rag_id}/chat/messages` — возвращает все сообщения по `(rag_id, user_id)` в хронологическом порядке.
- Frontend: `ChatView` запрашивает сообщения по `ragId`, выбора диалога (сессии) нет.
- Роли: доступ к RAG и чату проверяется через `_can_access_rag` (владелец или участник RagMember). Viewer не видит RAG, куда не приглашён.

---

## Роли и доступ (напоминание)

| Роль | RAG | Чат и сессии |
|------|-----|----------------|
| **Владелец** | Всё (CRUD, загрузка, approve, участники). | Чат и CRUD **своих** сессий. |
| **Editor** | Редактирование (загрузка, approve). | Чат и CRUD **своих** сессий. |
| **Viewer** | Только просмотр и чат. | Чат и CRUD **своих** сессий. |

Проверка на всех эндпоинтах чата/сессий: `_can_access_rag`. Сессии фильтруются по `user_id = current_user.id` — каждый видит только свои. Участник (viewer в т.ч.) не видит RAG и чаты, куда его не приглашали.

## Шаги

### ✅ 1. Миграция: таблица `chat_sessions` и поле `session_id` в `chat_messages`

**✅ 1.1** Таблица **chat_sessions**  
`id` (PK), `rag_id` (FK → rag_instances), `user_id` (FK → users), `title` (TEXT, nullable), `created_at` (TIMESTAMP WITH TIME ZONE). Индексы по `rag_id`, `user_id`.

**✅ 1.2** В **chat_messages** добавить `session_id` (FK → chat_sessions).  
Вариант A: `session_id` NOT NULL — миграция создаёт по одной «дефолтной» сессии на каждую пару (rag_id, user_id), у которой уже есть сообщения, и проставляет этим сообщениям `session_id`. Вариант B: `session_id` nullable — старые строки остаются с NULL; при выборке «сообщения без сессии» трактовать как один legacy-поток; новые сообщения писать только в сессию (backend создаёт сессию при первом сообщении, если не передан session_id). Выбрать один подход и описать в миграции.

**Действия:** модель `ChatSession` в `models.py`; миграция Alembic (create table + add column + при необходимости backfill); `alembic upgrade head`.

**Исполнение:** Выбран вариант A. В `code/backend/app/models.py` добавлена модель `ChatSession` (таблица `chat_sessions`: id, rag_id, user_id, title, created_at) и в модель `ChatMessage` добавлено поле `session_id` (FK → chat_sessions, ondelete=CASCADE). Создан файл миграции `code/backend/alembic/versions/b8c9d0e1f2a3_add_chat_sessions.py` (revises: a7b8c9d0e1f2): create_table chat_sessions с индексами по rag_id и user_id; add_column session_id в chat_messages (сначала nullable); backfill — для каждой пары (rag_id, user_id) из chat_messages создаётся одна сессия, сообщениям проставляется session_id; alter_column session_id NOT NULL, FK и индекс. **Применение миграции к БД (2026-02-22):** после деплоя backend на cr-ubu выполнено `docker exec ferag alembic -c /app/alembic.ini upgrade head` на сервере — миграция a7b8c9d0e1f2 → b8c9d0e1f2a3 применена к production БД.

### ✅ 2. Backend: CRUD сессий и привязка сообщений к сессии

**✅ 2.1** Модели ответа: например `ChatSessionListItem` (id, title, created_at), `ChatSessionDetail` (id, rag_id, user_id, title, created_at). Тело создания: `ChatSessionCreate` (title?).

**Исполнение:** В `code/backend/app/routers/rags.py` добавлены схемы: `ChatSessionCreate` (title | None), `ChatSessionListItem` (id, title, created_at), `ChatSessionDetail` (id, rag_id, user_id, title, created_at), `ChatSessionUpdate` (title | None). Импортирована модель `ChatSession`.

**✅ 2.2** Эндпоинты (все за проверкой `_can_access_rag`; выборки сессий — по `user_id = current_user.id`):

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/rags/{rag_id}/chat/sessions` | Создать сессию (body: title?). `user_id = current_user.id`. |
| GET | `/rags/{rag_id}/chat/sessions` | Список сессий текущего пользователя по RAG (например по created_at DESC). |
| GET | `/rags/{rag_id}/chat/sessions/{session_id}/messages` | Сообщения сессии. Проверка: сессия.rag_id == rag_id, сессия.user_id == current_user.id. |
| PATCH | `/rags/{rag_id}/chat/sessions/{session_id}` | Обновить title. Только своя сессия. |
| DELETE | `/rags/{rag_id}/chat/sessions/{session_id}` | Удалить сессию (и сообщения CASCADE или каскадным удалением). Только своя сессия. |

**Исполнение:** В `code/backend/app/routers/rags.py` добавлены хелперы `_get_default_session(db, rag_id, user_id)` (последняя сессия по created_at или новая с title=None) и `_get_session_for_user(db, session_id, rag_id, user_id)` (проверка принадлежности сессии). Реализованы эндпоинты: `POST /rags/{rag_id}/chat/sessions` (body опционально через Body(None)), `GET /rags/{rag_id}/chat/sessions`, `GET /rags/{rag_id}/chat/sessions/{session_id}/messages`, `PATCH /rags/{rag_id}/chat/sessions/{session_id}`, `DELETE /rags/{rag_id}/chat/sessions/{session_id}` (204). Все за `_can_access_rag`, выборки сессий по current_user.id.

**✅ 2.3** `POST /rags/{rag_id}/chat`: принимать в body опционально `session_id`. Если передан — писать сообщения в эту сессию (проверка: сессия принадлежит current_user и rag_id). Если не передан — использовать «дефолтную» сессию: последнюю по created_at для (rag_id, current_user.id) или создавать новую с title=null.

**Исполнение:** В `ChatRequest` добавлено поле `session_id: int | None = None`. В обработчике `chat()` при переданном session_id вызывается `_get_session_for_user`; при отсутствии — `_get_default_session`. Обе записи `ChatMessage` создаются с указанным `session_id`.

**✅ 2.4** `GET /rags/{rag_id}/chat/messages`: оставить для обратной совместимости или заменить на выборку по сессии. Если оставить — возвращать сообщения только из одной выбранной сессии не получится без параметра session_id. Рекомендация: ввести параметр запроса `session_id`; если передан — возвращать сообщения этой сессии (с проверкой доступа); если не передан — поведение «дефолтная/последняя сессия» (как в 2.3) и возврат её сообщений.

**Исполнение:** В эндпоинт `get_chat_messages` добавлен параметр запроса `session_id: int | None = None`. При переданном session_id — проверка через `_get_session_for_user`, выборка по `ChatMessage.session_id`; при отсутствии — разрешение дефолтной сессии через `_get_default_session` и выборка по ней. Обратная совместимость сохранена (вызов без session_id возвращает сообщения дефолтной/последней сессии).

**✅ 3.1** API: функции для сессий (например `getSessions(ragId)`, `createSession(ragId, title?)`, `getSessionMessages(ragId, sessionId)`, `updateSession(ragId, sessionId, title)`, `deleteSession(ragId, sessionId)`). Вызовы к эндпоинтам из п. 2.2 и 2.4.

**Исполнение:** В `code/frontend/src/api/chat.ts` добавлены интерфейс `ChatSessionListItem` и функции: `getSessions(ragId)`, `createSession(ragId, title?)`, `getSessionMessages(ragId, sessionId, limit?, offset?)`, `updateSession(ragId, sessionId, title)`, `deleteSession(ragId, sessionId)`. Функции `sendQuestion` и `getChatMessages` дополнены опциональным параметром `sessionId`.

**✅ 3.2** ChatView (или обёртка «Диалог»): при открытии запрашивать список сессий; отображать список диалогов (например боковая панель или выпадающий список). Кнопка «Новый диалог» → создание сессии, переход на неё. При выборе сессии — запрос сообщений `GET .../sessions/{id}/messages`, отображение в текущем виде (MessageBubble и т.д.). При отправке вопроса передавать в `POST /chat` выбранный `session_id`. Опционально: переименование сессии, удаление сессии (с подтверждением).

**Исполнение:** В `code/frontend/src/views/ChatView.vue` при открытии вызываются `loadSessions()` (GET sessions) и `loadMessages()` (по текущей сессии или дефолтной). Добавлена панель «Диалоги»: список сессий (отображение как «Диалог {id}» при пустом title), кнопка «+ Новый диалог» (createSession, переход на новую сессию, очистка сообщений), выбор сессии (watch по currentSessionId → loadMessages). При отправке вопроса передаётся `session_id` выбранной сессии; после первого сообщения без сессии выполняется перезагрузка списка сессий. Реализовано удаление сессии с подтверждением (confirm). **Переименование сессии в UI:** кнопка «✎» (Переименовать) у каждой сессии; по клику показывается инлайн-поле ввода с текущим title, сохранение по Enter или blur (`updateSession`), отмена по Escape; после сохранения локальный список сессий обновляется.

**✅ 3.3** Обратная совместимость: если у пользователя одна сессия (в т.ч. дефолтная) — можно не показывать выбор, а сразу подставлять эту сессию и загружать её сообщения, чтобы поведение совпадало с текущим «один поток».

**Исполнение:** Список диалогов отображается всегда; при одной сессии он содержит один пункт, логика выбора и загрузки сообщений совпадает с «один поток». При отсутствии сессий используется дефолтная сессия (backend при первом сообщении создаёт её), после ответа список сессий обновляется и currentSessionId выставляется.

## Критерии успеха

- Пользователь может создать несколько диалогов (сессий) по одному RAG и переключаться между ними.
- Сообщения сохраняются в выбранной сессии; после перезагрузки список сессий и сообщения выбранной сессии отображаются.
- Владелец, editor и viewer видят и правят только свои сессии; участник не видит RAG, куда не приглашён.
- Удаление сессии удаляет её сообщения; переименование сессии доступно.
