## Выполнено

### 1. Уточнение текущей картины (Fuseki + diagnose_rag_context)

- Скрипт `inventory_ferag_dataset.py`: SPARQL к датасету ferag-{rag_id}, список сущностей/связей и чек-лист по ключевым фактам.
- По ferag-00026: 9 сущностей, 13 связей; diagnose по 7 вопросам — baseline до правок (проблемы: год ACME, технологии хранилища в графе отсутствовали).

### 2. Улучшение индексации: GraphRAG → RDF → Fuseki

- **2.1** Скрипт `graphrag-test/analyze_parquet_for_rag.py`; анализ parquet: ключевые факты есть; маппинг в RDF использует title, type, description (entities) и source, target, description, weight (relationships).
- **2.2** В `graphrag-test/test_graphrag_to_rdf.py`: расширен type_map (LOCATION, CONCEPT, TECHNOLOGY, DATE); fallback описаний — при пустом description подставляются title (сущности) и «{source} — {target}» (связи).
- **2.3** По решению в чате — RAG 27 (новый граф, новый текст) для проверки. Цикл запущен через веб-интерфейс, подтверждён после обновления SSL-сертификата. **2.3.4** inventory и diagnose для RAG 27: 10 сущностей, 10 связей; нужные факты в контексте.

### 3. Улучшение retrieval в rag_context (вариант A)

- **3.1** В `rag_context.py`: словарь KEYWORD_SYNONYMS (рус→англ: основан/founded, технологии/technology, работает/works и др.); разбиение CamelCase (GraphRAG → graph, rag); убраны «работает»/«работать» из стоп-слов.
- **3.2** Лимиты 15→20 (ENTITY_LIMIT, RELATIONSHIP_LIMIT). Fallback переработан: при пустых ключевых словах — build_context_fixed(); при ключевых словах без совпадений — CONTEXT_NO_MATCH («По ключевым словам вопроса совпадений в графе не найдено»), чтобы не маскировать проблемы retrieval.

### 4. Проверка end-to-end

- **4.1** Повторная диагностика для RAG 27 по семи вопросам (адаптированным под корпус): все нужные факты в контексте; синонимы и CamelCase работают.
- **4.2** В веб-чате по RAG 27 заданы вопросы (Alice Brown, Bob Johnson, DataWeave Analytics — место/год/технологии, GraphRAG Infra, связь Alice и Bob). Ответы опираются на факты из графа.
