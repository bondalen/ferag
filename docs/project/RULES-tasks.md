# Правила формирования структуры задач проекта ferag

Документ задаёт модель задач, иерархию, нумерацию и правила для общих (зависимых) задач. Применяется к **вновь формулируемым** задачам; существующие задачи в [TASKS.md](../tasks/TASKS.md) не переписываются, если не противоречат правилам.

**Связанные документы:** [TASKS.md](../tasks/TASKS.md), [PROJECT.md](PROJECT.md).

---

## 1. Определения

**Задача** — действие, результатом которого является достижение требуемого **состояния** некоторого **объекта** (приложение в целом, подсистема, компонент, API, экран и т.д.).

**Объект** — то, над чем выполняется действие (приложение, backend, фронтенд, экран RAG, компонент «список приглашённых», эндпоинт API X и т.д.).

**Уровень задачи** — уровень объекта в иерархии «система → подсистема → компонент → …». Задача верхнего уровня относится к приложению в целом и может не иметь подзадач. Задача глубокого уровня относится к мелкому объекту и может иметь подзадачи на нескольких уровнях.

**Идентификатор задачи** — последовательность номеров через точку (например `27`, `4.8.11.5`). Каждый сегмент соответствует уровню вложенности по объекту/состоянию. Глубина не ограничена заранее.

---

## 2. Формулировка задач

- Каждую задачу формулировать в формате: **действие** + **объект** + **требуемое состояние** (или критерий приёмки).
- При необходимости в описании или в отдельном поле явно указывать **объект** и **целевое состояние** (что должно быть истинно по завершении).
- Уровень вложенности в каноническом дереве должен соответствовать уровню объекта.

---

## 3. Структура: DAG и ацикличность

**Структура задач — ориентированный ациклический граф (DAG), а не дерево.**

- Одна и та же задача (например, «реализовать эндпоинт API X») может быть **общей подзадачей** для нескольких других задач (несколько компонентов фронтенда используют этот API). У такой задачи может быть несколько «родителей» в графе зависимостей.
- **Ацикличность обязательна:** ни одна задача не может зависеть от себя (ни напрямую, ни через цепочку других задач). При добавлении зависимости выполняется проверка на циклы; при обнаружении цикла зависимость не добавляется.
- Проверка циклов выполняется по **каноническим ID** (см. п. 5).

---

## 4. Нумерация и каноническое дерево

- Каждый сегмент ID (например, 4, 8, 11, 5) — уровень вложенности по объекту/состоянию: от более общего к более частному. Номер в рамках одного родителя уникален.
- Задача без подзадач может иметь один номер (например `27`). Задача с подзадачами имеет составной ID (например `4.8.11`); подзадачи — `4.8.11.1`, `4.8.11.2` и т.д.
- **Каноническая задача** — задача, для которой описание, подзадачи и статус хранятся в одном месте (в «своём» дереве, например дереве backend или фронтенда). У каждой канонической задачи ровно одно каноническое место в иерархии.

---

## 5. Ссылки на каноническую задачу из другого дерева (нотация A*B)

Если в дереве разработки фронтенда (или ином дереве) некоторая вложенная задача по смыслу совпадает с канонической задачей из дерева backend (или другого раздела), её **не дублируют**, а оформляют как **ссылку** на каноническую задачу.

**Формат ссылки:** `A*B`, где  
- **A** — локальный путь в том дереве, где отображается зависимость (позиция в иерархии);  
- **B** — канонический ID задачи (источник истины).

**Примеры:**

- В дереве backend: задача `3.8.12` «реализовать эндпоинт API X» (каноническая, с подзадачами).
- В дереве фронтенда: задача `4.6.12.4` «разработать компонент 4», в ней вложенная задача «реализовать эндпоинт API X» с локальным номером `4.6.12.4.8`. Этой вложенной задаче присваивается ID **`4.6.12.4.8*3.8.12`**; структуру в дереве фронтенда не меняют. Редактирование описания и подзадач — только в дереве backend (3.8.12).
- Аналогично в задаче `4.6.12.8` «разработать компонент 8» вложенная задача «реализовать эндпоинт API X» с локальным путём, например, `4.6.12.8.12` → ID **`4.6.12.8.12*3.8.12`**.

**Семантика:**

| Аспект | Правило |
|--------|--------|
| Описание и подзадачи | Хранятся только у канонической задачи (B). |
| Статус | Один статус у B; все вхождения вида A*B считаются выполненными/не выполненными вместе с B. |
| Редактирование | Меняют только каноническую задачу (B). |
| Позиция в дереве | Локальный путь A сохраняет место в иерархии того раздела, где показывается зависимость; поддерево B в этом месте не дублируется. |

**Локальный путь A** должен быть валидным путём в том дереве, где стоит ссылка (родитель A существует, нумерация согласована).

---

## 6. Хранение зависимостей и отображение

- Зависимости между задачами (в т.ч. «задача X зависит от задачи Y») при необходимости ведут в отдельной таблице или в поле «Зависит от» (список канонических ID). При проверке ацикличности используются только канонические ID (для ссылки A*B берётся B).
- В дереве при отображении узел A*B можно показывать с пометкой «= B» или «→ B»; по клику или ссылке открывать каноническую задачу B.

---

## 7. Применение к существующим и новым задачам

- **Существующие задачи** в TASKS.md не переименовываются и не переформулируются ради приведения к этим правилам. Они считаются соответствующими модели «действие → состояние объекта», если не задано иное. Ссылочная нотация A*B и явная таблица зависимостей в текущем TASKS.md пока не используются.
- **Вновь формулируемые задачи** подчиняются настоящим правилам: формулировка (действие + объект + состояние), при необходимости — произвольная глубина ID, при общей подзадаче — ссылка A*B, при введении зависимостей — проверка ацикличности по каноническим ID.
